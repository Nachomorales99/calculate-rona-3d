# 0005 · Países y subdivisiones: dataset propio, sin API externa en runtime

2026-10-26 · aceptada

## Contexto

El usuario elige país y, según el país, provincia/estado/región (Argentina → 24 jurisdicciones: 23 provincias + CABA). Las APIs públicas gratuitas (CountriesNow, REST Countries) existen pero son terceros sin SLA, y el paquete npm `country-state-city` es GPL-3, incompatible con un producto comercial.

## Decisión

Un módulo `geo` en la API con **datos estáticos versionados en el repo** (`apps/api/src/modules/geo/data/countries.json` y `subdivisions.json`), generados **una vez** por un script (`pnpm geo:build`) a partir de fuentes públicas (ISO 3166-1 y 3166-2: REST Countries para países y moneda por defecto; CountriesNow o `iso-codes` de Debian para subdivisiones), revisados a mano para Argentina y los países del Cono Sur.

Endpoints públicos (sin auth, cacheables, `Cache-Control: max-age=86400`):

```
GET /geo/countries                      → [{ code: "AR", name: "Argentina", currency: "ARS", phone: "54", flag: "🇦🇷" }]
GET /geo/countries/AR/subdivisions      → [{ code: "AR-M", name: "Mendoza", type: "provincia" }]
```

El front los consume con TanStack Query y los guarda en caché; al elegir país se preselecciona la moneda de trabajo (editable).

## Consecuencias

- Cero dependencia externa en producción; funciona offline para la PWA una vez cacheado.
- Actualizar el dataset es correr el script y revisar el diff.
- Ciudades no se listan (demasiado volumen y poco valor): campo de texto libre con autocompletado futuro si hace falta.
